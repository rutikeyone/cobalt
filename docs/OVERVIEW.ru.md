# Cobalt подробно

То, чего нет в [README](../README.ru.md): все возможности, как это устроено внутри, что
покрывает обещание совместимости и сколько всё это стоит.

## Что это

Контейнер, который владеет тем, что построил. Скоупы образуют дерево, а не стек, поэтому у сессии,
флоу оформления заказа и экрана есть собственное время жизни, и конец одного уносит с собой всё, что
построено внутри: логаут — это `await scope.dispose()`, а не девять подписок на сессионный стрим и
четыре метода `reset()`, протёкших в доменные интерфейсы.

Кодогенерация — удобство поверх этого рантайма, а не второй фреймворк. Генератор пишет ровно то, что
вы написали бы руками, не пользуясь ничем, кроме публичного API `cobalt`, — именно это делает
возможной постепенную миграцию: сгенерированный и рукописный контейнеры композируются в одном графе.

## Возможности

| | |
|---|---|
| **Иерархические скоупы** | дерево, а не плоский стек — два независимых поддерева сосуществуют, чего стек выразить не может |
| **Владение и разбор** | скоуп освобождает построенное, LIFO по порядку **создания**, best-effort с одним дедлайном на всё дерево |
| **Двухфазный старт** | `@CobaltBootstrap` до появления контейнера, `@CobaltInit` внутри него, обе фазы дождаются до возврата из `start` |
| **Ленивые async-синглтоны** | строятся первым `getAsync`, а не на старте — для дорогого объекта, который живёт всё приложение, но нужен немногим экранам |
| **Async-транзиенты** | `registerAsyncFactory` или `@cobaltTransient` на классе с `@CobaltInit`: каждый `getAsync` строит и дожидается нового экземпляра, который скоуп не удерживает |
| **Топологический порядок** | async-инициализаторы разложены по уровням алгоритмом Кана; независимые ветки едут через `Future.wait`, цикл валит сборку с указанием цикла |
| **Property injection** | поля `late final`, заполняемые сгенерированным миксином: у класса с пятью зависимостями пустой конструктор |
| **Полнота на этапе сборки** | зависимость, которую никто не регистрирует, валит сборку, называя все пробелы разом |
| **Параметризованные регистрации** | `@CobaltParam` для того, что даёт место вызова; тип аргумента генератор пишет именованной записью. На `@CobaltInit`-классе сборка асинхронная, её ждут через `getAsyncWithParam` |
| **Опциональные зависимости** | `Foo?` резолвится через `getOrNull` и получает null вместо падения сборки |
| **Модули** | регистрация типов, которые написали не вы, — клиент из чужого пакета, значение из SDK |
| **Декораторы** | обёртка вокруг того, что отдаёт регистрация, — логирование, повторы, кэш — без правки её класса, руками или через `@CobaltDecorates`; одна регистрация или все регистрации типа |
| **Хуки** | видят каждый экземпляр супертипа, который строит граф, — например, каждый `Loggable` попадает в реестр, — какой бы регистрацией он ни был построен, вручную или через `@cobaltHookAll`; в отличие от декоратора, подменить экземпляр не могут |
| **Окружения** | одна абстракция, разная реализация по сборкам, пересечения отвергаются на сборке |
| **Именованные и мульти-инъекции** | квалификаторы `@Named` и `getAll<T>()` по всем регистрациям типа |
| **Наблюдаемость** | типизированные события, а не строки: логирование, структурированный приём и отчёты об ошибках со следом |
| **Инспектор внутри приложения** | живое дерево скоупов, что построено и с каким временем жизни, и всё, о чём сообщили |
| **Навигационные флоу** | скоуп, чьё время жизни — флоу go_router, и ничто не зеркалит роутер |
| **Плагин линтера** | восемнадцать правил на том же слое разбора, которым пользуется генератор |
| **Подмены** | замена регистрации там, где она принадлежит, так что двойника видит каждый потребитель — в тесте, флейворе или debug-меню |
| **Хелперы для тестов** | скоупы, разбирающиеся вместе с тестом, и подмены, работающие так же, как в продакшене |
| **Нет глобального контейнера** | ничего не лежит в окружении, поэтому тесты идут параллельно, а два графа в одном процессе не связаны |

## Требования

**Каждый пакет требует Dart `^3.10.0`, а тем, кому нужен Flutter, — `>=3.38.0`.** Все пятнадцать,
включая генератор и плагин линтера: приложение, оставшееся на Flutter 3.38, получает оба режима, а
не только Manual Mode.

Разрабатывается на Flutter 3.38.9 — на самом полу — и проверяется на текущих `stable` и `beta`.

За полом стоит механизм, который стоит знать, потому что связывает не версия Dart.
**Flutter 3.38 пиннит `meta 1.17.0`, а analyzer 10.0.2 просит `^1.18.0`** — значит Flutter-приложение
на 3.38 упирается в analyzer 10.0.1, что бы ни было написано в его SDK-констрейнте. Потребитель на
чистом Dart этим не связан и берёт 12.1.0; 13.0.0 недостижим для обоих, потому что тянет
`_fe_analyzer_shared 100`, которому нужен Dart 3.11.

Поэтому три инструментальных пакета объявляют `analyzer: ">=10.0.1 <15.0.0"`, а не одну версию, и
один и тот же исходник собирается и проходит тесты на каждой строке этого диапазона. Каждый пакет,
читающий анализатор, пиннит его точно — так что какую строку вы получите, решает ваш проект, а не мы:

| ваш проект | analyzer | analyzer_plugin | analysis_server_plugin | analyzer_testing | dart_style |
|---|---|---|---|---|---|
| Flutter 3.38 | 10.0.1 | 0.14.1 | 0.3.7 | 0.1.9 | 3.1.7 |
| что-то новее, пока ничто другое не требует analyzer 13 | 12.1.0 | 0.14.8 | 0.3.14 | 0.2.5 | 3.1.8 |
| `test` из Flutter 3.49, `build` 4.0.8+, свежие `freezed` или `json_serializable` | 13.x – 14.x | 0.14.9 – 0.14.17 | 0.3.15 – 0.3.23 | 0.2.6 – 0.4.2 | 3.1.9 – 3.1.13 |

Генератор форматирует с фиксированной версией языка, 3.10, а не с той, которую резолвнутый
`dart_style` считает последней. Поэтому каждая строка даёт одинаковые байты, и релиз форматтера с
новыми правилами стиля для более новой версии языка не меняет закоммиченное. Это проверяется, а не
предполагается: job `verify` в CI пересобирает на Flutter 3.38.9, где `codegen_basics` попадает на
строку 10.0.1, а стенд совместимости — на 12.1.0, и сверяет с закоммиченным; job `forward` на
`beta` резолвит самую новую строку и сверяет те же файлы.

Репозиторий разрабатывается на этом полу, и поэтому он не pub workspace. Workspace — это одна
резолюция, а на Flutter 3.38 `flutter_test` пиннит `test_api 0.7.7`, что ограничивает раннер `test`
версией 1.26.3 и анализатор — ниже 9, тогда как `cobalt_analyzer` нужен 10.0.1. Поэтому каждый пакет
резолвится сам и берёт соседей из `pubspec_overrides.yaml`, который пишет `tool/overrides.py`. Job
`verify` в CI гоняет всё на Flutter 3.38.9, а `forward` — на `stable` и `beta`, чтобы заранее
увидеть, что впереди, а не матрицу прошлых релизов.

## Совместимость

Ломает только мажорный релиз, и его CHANGELOG перечисляет это под **Breaking**. В релизах 0.x
ломать мог любой минорный; с 1.0 — ни один. Три правила о том, что это значит:

- **Новое значение публичного перечисления — минорное изменение.** `CobaltRegistrationKind` рос в
  трёх релизах и ещё вырастет. Спрашивайте его свойства — `isRetained`, `takesParam`, `isAsync`,
  `isBuiltByInit` — вместо `switch` по значениям; исчерпывающий `switch` обновлять вам.
- **`CobaltResolver` нельзя реализовать вне Cobalt.** Это `base`-класс, поэтому новый способ
  резолва приходит в минорном релизе. В тесте строится настоящий скоуп — `cobaltTestRoot` из
  `cobalt_test`, — а не мок.
- **Новый хук наблюдателя — минорное изменение.** `CobaltObserver` — базовый класс с пустыми хуками,
  так что наблюдатель, написанный под старый релиз, продолжает компилироваться (так появился
  `onInstanceBuilt`); `CobaltHook` устроен так же. Всё, что вы *реализуете*, — фабрики, декораторы, приёмники логов,
  `Disposable` — получает новые члены только в мажорном релизе.

Две вещи вне этих правил намеренно. `debug*`-члены `CobaltScope` — то, через что граф читают
инспектор и `cobalt_test`, — помечены `@experimental` и могут меняться в минорном релизе; новые
анализаторы отмечают каждое их использование в вашем коде как `experimental_member_use` — в этом и
смысл, подавляйте там, где это осознанно. А
`cobalt_analyzer` — внутренний пакет генератора и плагина линтера: его API следует их нуждам, а не
semver; зависьте от них, а не от него.

Переходите со старого 0.x — [MIGRATION](../MIGRATION.ru.md#с-cobalt-0x-на-10) перечисляет каждое
изменение, после которого код перестаёт компилироваться, и что с ним делать.

`tool/api.sh` показывает, что изменилось в каждом пакете относительно версии на pub.dev, а
`tool/class_modifiers.txt` хранит модификаторы классов всех публичных типов — то единственное, чего
этот инструмент не видит, — и CI падает, пока изменённый модификатор не записан.

## Производительность

Cobalt рядом с get_it — из [`benchmark/`](../benchmark/README.md), там же описано, что делает каждая
строка. Сборка AOT, arm64, Dart SDK 3.10.8 (stable, `macos_arm64`). Медиана трёх прогонов; они расходились не
больше чем на десять процентов.

| | Cobalt | get_it | Cobalt / get_it |
|---|---:|---:|---:|
| get уже построенного синглтона | 81 ns | 425 ns | 0.19× |
| сборка transient с двумя зависимостями | 356 ns | 1.22 µs | 0.29× |
| 200 регистраций, затем get каждой | 137 µs | 386 µs | 0.35× |
| старт 20 async-синглтонов | 24.7 µs | 28.1 µs | 0.88× |
| тот же transient с пустым наблюдателем | 374 ns | — | — |
| тот же transient с записывающим наблюдателем | 860 ns | — | — |
| тот же transient с наблюдателем журнала на уровне по умолчанию | 385 ns | — | — |

Меньше 1 в последнем столбце — Cobalt потратил меньше времени. Абсолютные числа принадлежат этой
машине; переносится порядок величин. Резолв
стоит заметно меньше микросекунды, граф из 200 регистраций — доли миллисекунды, асинхронный старт
двадцати синглтонов — десятки микросекунд; на фоне кадра в 16 мс ничего из этого не видно.
Наблюдатель, который превращает каждое событие в запись, примерно удваивает стоимость сборки;
наблюдатель журнала на уровне по умолчанию — нет: записи о каждом экземпляре, которые он отбрасывает,
даже не создаются, и он стоит столько же, сколько наблюдатель, который ничего не переопределяет.

```
cd benchmark && dart compile exe bin/main.dart -o /tmp/cobalt_benchmark && /tmp/cobalt_benchmark
```

## Как это устроено

### Скоуп владеет тем, что построил

Скоуп — это узел с родителем, детьми и собственными регистрациями. Резолв идёт вверх, поэтому
регистрация в ребёнке затеняет ту, что выше, — так репозиторий сессии заменяет анонимный в
продакшене. Фабрика выполняется на скоупе, которому принадлежит её регистрация, поэтому затенение
достаёт только до того, что резолвится ниже; чтобы заменить зависимость для всех, override отдают
скоупу-владельцу ключа, и настоящая регистрация там пропускается.

Разбор — LIFO по порядку **создания**, а не объявления. Это различие и есть баг большинства
рукописных контейнеров: компонент, объявленный первым и созданный последним, умирает первым, пока от
него ещё кто-то зависит. И разбор best-effort: упавший `dispose` записывается, остальные всё равно
выполняются, у всего дерева один дедлайн, а несделанное перечисляется в `CobaltDisposeError` вместо
того, чтобы первая ошибка спрятала остальные девять.

Родитель держит детей сильно. Слабые ссылки рассматривались и отвергнуты: они позволили бы GC забрать
дочерний скоуп до вызова `dispose()`, то есть не вызвать его никогда, и от утечек всё равно не
спасают — живые объекты внутри держат себя сами.

### Граф проверяется до того, как соберётся

Code-Gen Mode отвергает неполный граф на сборке, называя все пробелы одним сообщением:

```
Diagnostics requires DeviceInfo, which nothing registers. Annotate the class that
provides it with @CobaltInject, or name it in @CobaltScopeRoot(provides: [...]) when
something outside the generated container registers it.
```

Считаются параметры конструктора, `@injected`-поля и `@CobaltInit(dependsOn:)`, квалификатор `@Named`
входит в ключ, а каждое окружение проверяется отдельно. Дубликаты регистраций, циклы зависимостей,
два корня скоупа в одном пакете, generic-класс и абстрактный класс под `@CobaltInject` — тоже ошибки
сборки.

Это гарантия Code-Gen, и граница названа честно: рукописная фабрика резолвит внутри `create`, поэтому
статически не видно, что она попросит. Графы Manual Mode по-прежнему падают в рантайме — ровно под
этот пробел в `cobalt_test` есть `expectGraphResolves`.

### Сгенерированный код — это то, что вы написали бы сами

Три билдера: один пишет миксины property injection, второй сканирует каждую библиотеку в IR, третий
собирает весь пакет в `lib/cobalt.g.dart`. Агрегация двухфазная потому, что один шаг сборки не видит
программу целиком.

На выходе приватные const-фабрики и `$CobaltRootScope`, упорядоченный компайл-тайм топологической
сортировкой, — ни замыканий, ни рефлексии, ни сканирования в рантайме. `$cobaltBootstrap` — геттер, а
не хранимый список, поэтому рестарт получает свежие шаги, а не те, что прошлый старт уже израсходовал.

Дженерики работают как зависимости и как цели `exposeAs`: `Repository<User>` и `Repository<Order>` —
две регистрации, потому что `CobaltKey` строится из `Type`, а это разные типы. Сам инъектируемый класс
generic быть не может: генератору никто не говорит, какие инстанциации регистрировать.

`cobalt_analyzer` существует затем, чтобы генератор и линтер разбирали объявления Cobalt **одной**
реализацией, а не двумя, которые неизбежно разойдутся. Он владеет IR и топологической сортировкой и
не зависит ни от `build`, ни от API плагина.

**Инвариант проекта:** сгенерированный код имеет право использовать только публичный API `cobalt`.
В тот момент, когда генерации понадобится что-то, чего не выражает Manual Mode, это два разных
фреймворка под одним именем.

### Наблюдаемость — это типизированные события

`CobaltObserver` сообщает, что делает граф: появляются скоупы, строятся инстансы, завершается старт,
падает разбор. В колбэки приходят описатели, а не живые объекты, потому что наблюдатель, способный
резолвить из скоупа посреди разбора, уже не наблюдает; а исключение из колбэка проглатывается:
наблюдение не должно ломать наблюдаемое.

Записи несут `kind` как значение, а не как предложение, — именно это позволяет структурированному
приёмнику ключеваться на `CobaltEventKind.scopeInitFailed`, не разбирая прозу. Лог-sink — это один
колбэк, поэтому ни один логгер не остаётся за бортом из-за отсутствия пакета-адаптера; у
крашрепортинга форма своя, потому что полезным отчёт делает след того, что граф делал перед этим.

Когда наблюдателей нет, цена каждого события — одна проверка пустого списка.

### Навигационные флоу

`cobalt_go_router` делает время жизни скоупа навигационным флоу: создан при входе, разобран при
выходе. Это обычный наследник `ShellRoute`, а скоупом владеет виджет внутри него — ничто не слушает
роутер и не зеркалит его, потому что именно на зеркалировании рукописные версии ломаются на кнопке
«назад», на deep links и на переключении вкладок.

Флоу из маршрутов верхнего уровня без общего пути — `/cart`, `/checkout`, `/payment` — тоже один
шелл: у `ShellRoute` нет собственного пути, и URL остаются такими, как объявлены. Недостижимы только
маршрут, общий для двух флоу, и граница, которую решает рантайм, а не таблица маршрутов, — см.
README пакета.

## Примеры

Одно приложение запускает их все:

```bash
cd examples/gallery && flutter run
```

Галерея организована по **возможностям**, а не по проектам: читатель приходит узнать, как кончаются
скоупы, а не посмотреть на `notes_app`. Семнадцать записей в шести секциях:

| Секция | Записи |
|---|---|
| Старт | Двухфазный старт · Окружения · Ленивый async · Async-транзиент |
| Инъекция | Property injection · Именованные и мульти-инъекции · Декораторы |
| Скоупы и время жизни | Скоуп на виджете · Сессионный скоуп · Дерево скоупов · Навигационные флоу · Разбор |
| Кодогенерация | Сгенерированный контейнер · Manual Mode |
| Наблюдаемость | События графа · Инспектор в приложении |
| Тестирование | Тестовые паттерны |

Каждая запись с интерфейсом открывается со **своим** графом: он строится при входе и разбирается при
выходе. Откройте две — их деревья скоупов не связаны, и это ровно то, ради чего галерея существует.
Три записи без интерфейса (`Разбор`, `Manual Mode`, `Тестовые паттерны`) показывают вывод в консоль
вместо кнопки, потому что галерея, предлагающая «открыть» CLI, врала бы.

Галерея написана на английском, русском, китайском и корейском, язык переключается на хабе — и то же верно для
каждого экрана, который она монтирует. Каждый пример несёт свои `l10n/*.arb` и генерирует свой
делегат, который галерея собирает рядом со своим и с делегатом инспектора; так и выглядит настоящее
многопакетное Flutter-приложение.

Записи журнала самого фреймворка остаются английскими, как и идентификаторы на экране — имена шагов,
имена скоупов, ключи регистраций, времена жизни. Что именно остаётся словами Cobalt и почему — в
[README `cobalt_inspector`](../packages/cobalt_inspector/README.md), а как устроены примеры — в
[README галереи](../examples/gallery/README.md).

Восемнадцать правил плагина линтера перечислены в
[README `cobalt_lint`](../packages/cobalt_lint/README.md) и в
[GUIDE_CODEGEN.ru.md](../GUIDE_CODEGEN.ru.md#16-плагин-линтера).
